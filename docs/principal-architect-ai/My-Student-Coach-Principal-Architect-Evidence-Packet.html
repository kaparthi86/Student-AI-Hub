01-product-ownership/PRD-my-student-coach.md

PRD — My Student Coach (Student AI)

Field Value
Document ID PRD-MSC-2026-01
Owner Product / Principal Architect (AI)
Status Living — aligned to shipped main as of 2026-11-08
Primary users Middle school → college / exam prep students
Success definition Students complete a study turn (ask → understand → practice) without leaving the product

1. Problem

General-purpose AI chat is abundant and often harmful for schoolwork: long unfocused answers, brand confusion, submission-ready solutions, and weak grounding in the student’s own notes. Students need a study coach that answers first, teaches the smallest useful next step, respects honor code, and works on phone and laptop.

2. Goals

Priority Goal Measurable signal
P0 Fast authenticated access to Ask / Code / Notebook Time-to-first-answer after Google login
P0 Clear, non-markdown-noisy answers with brand identity Thumbs-up rate; “**” strip failures = 0
P0 Mobile-simple shell (Home / Tutor / Learning / Profile) Mobile session completion
P1 Learning labs (Voice, Flashcards, Math, Focus, Gaps) Lab weekly active use
P1 Conversational Voice Tutor Turns per voice session ≥ 3
P2 Play-ready Android (TWA/PWA path) Install / add-to-home rate

3. Non-goals

  • Replacing a school LMS or gradebook
  • Native Kotlin app before PWA/TWA product-market fit
  • General consumer search engine
  • Finance / Budget AI (removed — Student AI wedge only)
  • Claiming to be ChatGPT / Claude / Perplexity / Google

4. Personas

  1. Exam-focused high schooler — needs short explanations, quiz mode, flashcards.
  2. College CS student — needs Code tutor + Practice loop without full homework dumps.
  3. Note-heavy learner — uploads PDFs/notes; needs Notebook grounded answers.
  4. Voice learner — wants talk-back study while commuting (Chrome/Edge).

5. Product surface (shipped)

Surface Job to be done
Home Orient, resume last study path
Ask (Tutor) Explain / Guide / Quiz with live-web optional grounding
Code Patient coding tutor + practice
Notebook Multi-file analyze + grounded follow-ups
Voice Tutor Stream → speak-early → auto-listen → barge-in
Flashcards / Math / Focus / Gaps P1 labs under Learning
Profile Learner personalization (grade, subjects, explain style)
Login gateway One-screen Google join + honor / nonprofit disclaimer

6. Constraints

  • Open-source / cost-aware inference via Hugging Face Inference Providers
  • Supabase Google OAuth; no custom password store
  • Honor code: Guide/Quiz must not hand over submittable work
  • Privacy: feedback may go to Supabase or local feedback.ndjson
  • Browser voice APIs only for v1 conversational voice (no realtime native yet)

7. Risks and mitigations

Risk Mitigation
Model hallucination on homework Notebook “Not in document”; live-web source chips; honor modes
Inference cost Response cache TTL, prompt-cache params, voiceMode max tokens
Auth fragility (Safari) Redirect URL checklist; declared abort controllers; hard-refresh cache bust
Scope creep (hub of hubs) Wedge: Student AI only; kill Finance / Neo Clouds / Privacy from primary path

8. Launch criteria (public)

  • [x] Google login on production URL
  • [x] Ask / Code / Notebook streaming paths
  • [x] Privacy + Terms pages
  • [x] Feedback path (/api/feedback + weekly review SQL)
  • [x] Mobile bottom nav + Voice conversational loop
  • [ ] Production HF usage dashboard linked in cost pack
  • [ ] Android Play listing (TWA) after install metrics

9. Open questions

  1. Default study mode for new users: Explain vs Guide?
  2. Should live web be on by default for Ask?
  3. When to move Voice Tutor to a realtime STT/TTS provider?

01-product-ownership/decision-records/ADR-001-hf-inference-router.md

ADR-001 — Hugging Face Inference Providers (Router) as primary LLM path

Field Value
Status Accepted
Date 2026-05 (established) · reaffirmed 2026-11
Deciders Principal Architect / Founding engineer

Context

The product needs chat completions (streaming + JSON), optional vision, and cost control without operating GPUs.

Decision

Use Hugging Face Router https://router.huggingface.co/v1/chat/completions with env-selected Hub model IDs that include a routing suffix (e.g. deepseek-ai/DeepSeek-V4-Pro:fastest). Optional HF_MODEL_VISION for image turns.

Consequences

  • + OpenAI-compatible payload shape; easy SSE streaming
  • + Provider flexibility via Hub routing suffixes (:fastest, :groq, …)
  • + Aligns with student/nonprofit cost posture
  • − Model availability depends on enabled Inference Providers
  • − Operational debugging for 401 / model_not_supported must be first-class (implemented in server.js)

01-product-ownership/decision-records/ADR-003-response-and-prompt-cache.md

ADR-003 — Server response cache + optional prompt-cache params

Field Value
Status Accepted
Date 2026
Code completionCacheGet/Set, HF_RESPONSE_CACHE_TTL_SEC, HF_FORWARD_PROMPT_CACHE_PARAMS

Context

Repeated student questions (same mode + similar history) and notebook follow-ups burn tokens. Providers may also support prompt-prefix caching.

Decision

  1. Hash (model, kind, userKey, messages) and cache completed JSON/SSE payloads in-process with TTL + max entries.
  2. Skip cache for live-web turns (freshness).
  3. Optionally forward provider prompt-cache knobs when enabled.
  4. Prefer static system prefixes (Notebook static system) for prefix-cache friendliness.

Consequences

  • + Lower HF bill and latency on repeats
  • + Auditable via usage + hit logs for cost claims pack
  • − In-process cache does not share across multi-instance hosts (acceptable for MVP; Redis later)
  • − Stale answers if TTL too high — tune with HF_RESPONSE_CACHE_TTL_SEC

01-product-ownership/decision-records/ADR-004-pwa-before-native.md

ADR-004 — PWA / Android-simple shell before native Kotlin

Field Value
Status Accepted
Date 2026-11
Evidence android-shell.css, bottom nav, webmanifest, PR #74

Context

Play-ready presence is desirable, but a full Kotlin rewrite would freeze product learning velocity.

Decision

Ship an Android-simple web shell (bottom nav Home / Tutor / Learning / Profile, large tap targets, conversational Voice Tutor on Web Speech APIs) and treat TWA as the Play packaging path. Defer native realtime voice and Kotlin UI until install/retention justify it.

Consequences

  • − Voice quality limited by browser STT/TTS
  • − Some Safari Web Speech gaps — document Chrome/Edge as best voice path

01-product-ownership/decision-records/ADR-005-voice-conversational-loop.md

ADR-005 — Almost-conversational Voice Tutor (stream + speak-early)

Field Value
Status Accepted
Date 2026-11-08
Evidence PR #74; public/coach-labs.js; voiceMode in server.js

Context

Turn-based “listen → wait for full answer → speak all” feels like a walkie-talkie, not a tutor.

Decision

  1. Stream /api/chat with voiceMode: true.
  2. Speak sentence boundaries as tokens arrive.
  3. Auto-relisten after TTS when enabled.
  4. Barge-in: mic tap aborts fetch + cancels speech.
  5. Cap spoken length and server max_tokens (~280) for short replies.

Consequences

  • + Perceived latency drops dramatically
  • + Lower token spend vs long essay answers
  • − Sentence segmentation heuristics can mis-chunk abbreviations
  • − Not true full-duplex realtime; native path remains Later roadmap

02-technical-originality/prompt-library-export.md

Prompt Library Export (from server.js)

Exported for originality / IP evidence. Source of truth remains the repository. Do not treat this file as the runtime config.

Brand identity (all chat modes)

You are My Student Coach. If asked which product or model produced this response, answer: "This answer is from My Student Coach." … Never claim to be Perplexity, ChatGPT, Claude, Google, or any other brand.

Ask contract (summary)

  1. Direct answer first (1–2 sentences).
  2. Smallest useful explanation (~180 words default unless depth requested).
  3. Numbered steps for sequences; hyphen bullets for lists.
  4. Call out one misconception when relevant.
  5. No filler openers; no ** emphasis.

Code contract (summary)

Patient coding tutor; Markdown fences for code only; numbered procedures; honor Guide/Quiz constraints.

Math & Science contract (summary)

Numbered reasoning; formulas/units; common mistakes line; one similar practice prompt.

Study mode styles

Mode Instruction intent
Explain Full response contract
Quiz One check question; don’t reveal answer early; honor code
Guide Hints/questions only; no final answer / submittable code

Voice mode

Keep entire answer under ~80 words; 2–4 short spoken sentences; no markdown/lists; end with one short follow-up question; server caps ~280 max_tokens.

Notebook analyze (structured)

Exact ## sections in order:

  1. Executive summary
  2. Key concepts
  3. Formulas and procedures
  4. Practice checks (exactly 5)
  5. 7-day study plan

Rule: use only source materials; else “Not in document”.

Notebook follow-up

Document-grounded; start with direct answer; no invented citations; identity line as My Student Coach.

Learner profile injection

When present, include grade level, subjects, and explain style (balanced | simple | steps | examples) so the model personalizes without storing long memory server-side by default.

Live web appendix

When live web is requested and configured, append retrieved snippets and require grounding + source-aware answering (client shows source chips).

02-technical-originality/model-provider-choices.md

Model & Provider Choices

Primary path

Knob Default / pattern Role
HF_CHAT_URL https://router.huggingface.co/v1/chat/completions OpenAI-compatible router
HF_MODEL deepseek-ai/DeepSeek-V4-Pro:fastest (env-overridable) Text + chat
HF_MODEL_VISION optional Hub id with routing suffix Image turns
Routing suffix :fastest, :groq, etc. Required by Inference Providers

Why Hugging Face Inference Providers

  1. Cost leverage — open models; switch providers via suffix without rewriting the app.
  2. Operational fit — single token (HF_API_TOKEN) with Inference permissions.
  3. Streaming — SSE compatible with the coach UI stop/abort UX.

04-ai-cost-claims/cost-methodology.md

AI Cost Claims — Methodology

Principle

Cost claims for interviews or boards must be reproducible: invoice → usage export → calculation sheet → architecture lever (cache, max_tokens, model).

Sources of truth

Artifact Where it comes from Stored in git?
Provider invoices Hugging Face billing PDF/CSV No (sensitive) — store path in checklist
Usage export HF usage dashboard / API Template CSV only
Cache logs Server logs when HF_LOG_PROMPT_CACHE_USAGE enabled; completion cache hit counters Aggregate stats OK
Calculation spreadsheet cost-model.csv + your filled copy Template yes; filled copy optional/private
Before/after Same workload scripted against two configs Yes (methodology + sample)

Unit economics model

Monthly_AI_cost ≈ Σ ( prompt_tokens_i + completion_tokens_i ) × price_tier_i
Effective_cost_per_study_turn = Monthly_AI_cost / study_turns
Cache_savings = tokens_avoided_by_hits × price
Voice_savings ≈ (baseline_completion_tokens − voiceMode_completion_tokens) × voice_turns × price

Architectural levers already shipped

  1. Completion response cache — HF_RESPONSE_CACHE_TTL_SEC, HF_RESPONSE_CACHE_MAX_ENTRIES
  2. Prompt-cache param forwarding — HF_FORWARD_PROMPT_CACHE_PARAMS
  3. Static Notebook system prefix — prefix-cache friendly
  4. voiceMode max_tokens ≈ 280 + short-reply instruction
  5. Mode-specific max_tokens — vision/notebook/live-web caps in server.js
  6. Skip cache on live web — correctness over thrift when freshness matters

Claim language (safe)

  • Prefer: “We designed X to reduce completion tokens / avoid repeat HF calls; measured on [date] with [export].”
  • Avoid: absolute savings percentages without the CSV attached.
